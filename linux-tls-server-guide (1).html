PHASE 01 Provision your server
✓
STEP 01
Create a VPS (Virtual Private Server)
DigitalOcean, Linode, or AWS free tier
Infrastructure~15 min
▼
Why this matters for your portfolioEvery real production system lives on a server like this. Knowing how to spin one up and lock it down is table-stakes for any security engineering role. You're starting where every real deployment starts.

Go to DigitalOcean.com (cheapest, easiest for beginners — $5/month Droplet). Create an account, then create a new Droplet with these settings:

  • Image: Ubuntu 22.04 LTS x64 (LTS = Long Term Support — production standard)
  • Size: Basic, Regular, $5/mo (1 GB RAM, 1 CPU — plenty for this project)
  • Authentication: SSH Key (NOT password — you'll add your key next)
  • Region: Any — pick closest to you
  • Hostname: something like security-lab-01

If you don't have an SSH key yet, generate one on your local machine first:

bash — run on your LOCAL machine
# Generate an SSH key pair (RSA 4096-bit)
ssh-keygen -t ed25519 -C "your-email@example.com"
# When prompted for file location, press Enter (use default)
# Set a passphrase — this protects your private key

# View your PUBLIC key to paste into DigitalOcean
cat ~/.ssh/id_ed25519.pub
Security noteYou are generating a key PAIR. The .pub file (public key) goes on the server. The private key (id_ed25519) NEVER leaves your machine. This is asymmetric cryptography in action — your first real crypto concept applied.

Paste the output of cat ~/.ssh/id_ed25519.pub into DigitalOcean's SSH key field when creating the Droplet. Note the server's IP address when it's created.

STEP 02
First login & create a non-root user
Never operate as root in production
Access Control~10 min
▼
Why this mattersRunning as root means any bug, misconfiguration, or compromise immediately has full system access. Principle of least privilege — every security framework demands it. This is IAM in practice at the OS level.
bash — replace YOUR_SERVER_IP with your Droplet IP
# Connect to your server as root (first time only)
ssh root@YOUR_SERVER_IP

# Update all packages immediately
apt update && apt upgrade -y

# Create a new admin user (replace 'secadmin' with your username)
adduser secadmin

# Add user to sudo group (so they can run admin commands)
usermod -aG sudo secadmin

# Copy root's SSH key to the new user
rsync --archive --chown=secadmin:secadmin ~/.ssh /home/secadmin

# Test login as new user (open a NEW terminal tab — don't close this one yet)
# ssh secadmin@YOUR_SERVER_IP
Verify before continuingOpen a new terminal and run: ssh secadmin@YOUR_SERVER_IP. If you can log in successfully, you're good. Test sudo works: sudo whoami should return "root". Only then proceed.
PHASE 02 Secure SSH access
✓
STEP 03
Harden SSH configuration
Disable root login, passwords, change port
HardeningAuthentication~15 min
▼
Why this mattersSSH is the primary attack surface of any internet-facing server. Within minutes of a server going live, bots are attempting password logins. These settings eliminate entire attack classes: brute-force, credential stuffing, and direct root access.

Log in as your new non-root user, then edit the SSH config:

bash — logged in as secadmin
# Open SSH daemon config
sudo nano /etc/ssh/sshd_config

Find and change these lines (use Ctrl+W to search in nano):

/etc/ssh/sshd_config — changes to make
# Disable root login completely
PermitRootLogin no

# Disable password authentication (SSH keys only)
PasswordAuthentication no

# Disable empty passwords
PermitEmptyPasswords no

# Only allow your user
AllowUsers secadmin

# Reduce login grace time
LoginGraceTime 20

# Limit auth attempts per connection
MaxAuthTries 3

# Disable X11 forwarding (not needed)
X11Forwarding no
bash — save and restart SSH
# Save: Ctrl+O then Enter. Exit: Ctrl+X

# Test config is valid BEFORE restarting
sudo sshd -t

# If no errors, restart SSH service
sudo systemctl restart ssh

# Verify SSH is running
sudo systemctl status ssh
Do NOT close your current sessionOpen a new terminal tab and test login. If it works, you're safe. If locked out, your current session can fix things. Closing before testing = potential lockout.
PHASE 03 Firewall setup
✓
STEP 04
Configure UFW firewall
Allow only SSH, HTTP, HTTPS — block everything else
Network Security~10 min
▼
Why this mattersDefault-deny network policy: block all inbound traffic, then explicitly allow only what's needed. This is the firewall equivalent of zero-trust architecture — every employer will look for this mindset.
bash
# Default: deny all incoming, allow all outgoing
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH (CRITICAL — do this before enabling UFW)
sudo ufw allow ssh

# Allow HTTP and HTTPS (for your web server)
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Enable the firewall
sudo ufw enable

# Verify rules
sudo ufw status verbose
Expected outputYou should see Status: active, with rules for 22 (SSH), 80 (HTTP), and 443 (HTTPS). Everything else is denied by default.

Check what's actually listening on your server — this is how you audit your own attack surface:

bash — audit open ports
# Show all listening ports and which process owns them
sudo ss -tlnp

# You should only see: sshd on :22, nothing else yet

PHASE 05 Domain & DNS
✓
STEP 06
Point a domain at your server
Required for Let's Encrypt (TLS needs a domain)
DNS~20 min
▼
Why a domain is requiredLet's Encrypt issues certificates for domain names, not IP addresses. This is by design — the CA verifies you control the domain before trusting you with a certificate. This is the CA trust model your mentor mentioned.

Get a cheap domain from Namecheap (~$1–10/year) or use a free subdomain from Afraid.org. Then add these DNS A records:

DNS records to create
# At your domain registrar, create these A records:

Type   Name   Value              TTL
A      @      YOUR_SERVER_IP     3600
A      www    YOUR_SERVER_IP     3600

# @ means the root domain (yourdomain.com)
# www means www.yourdomain.com

Wait 5–30 minutes for DNS to propagate, then verify:

bash — verify DNS propagation
# Check DNS resolves to your IP
dig yourdomain.com +short

# Should return your server IP
# Also test:
curl -I http://yourdomain.com
# Should return HTTP 200 from your Nginx server
Don't proceed until DNS worksLet's Encrypt will fail if it can't reach your domain. Confirm dig yourdomain.com returns your server IP before moving on.
PHASE 06 Let's Encrypt TLS Certificate
✓
STEP 07
Install Certbot and obtain your certificate
Free, automated, trusted TLS certificate
TLSCertificatesCA~15 min
▼
What's actually happening hereCertbot contacts Let's Encrypt (a public CA). Let's Encrypt challenges your server to prove you control the domain (HTTP-01 challenge — it checks for a specific file at /.well-known/acme-challenge/). If you pass, it issues a signed certificate. This is the ACME protocol — automated certificate issuance. Understanding this is core to the CA knowledge your mentor mentioned.
bash
# Install Certbot and Nginx plugin
sudo apt install certbot python3-certbot-nginx -y

# Obtain certificate (replace with your domain)
sudo certbot --nginx -d yourdomain.com -d www.yourdomain.com

# Certbot will:
# 1. Ask for your email (for renewal reminders)
# 2. Ask you to agree to Terms of Service
# 3. Perform the domain validation challenge
# 4. Issue the certificate
# 5. Automatically modify your Nginx config
# 6. Ask if you want to redirect HTTP to HTTPS (say YES — option 2)
Success looks like thisCertbot will print "Congratulations! Your certificate and chain have been saved at: /etc/letsencrypt/live/yourdomain.com/". Visit https://yourdomain.com — you should see a padlock in the browser.

Inspect your certificate to understand what was actually issued:

bash — inspect your certificate
# List your certificates
sudo certbot certificates

# Inspect the actual certificate file (read the fields)
sudo openssl x509 -in /etc/letsencrypt/live/yourdomain.com/cert.pem \
  -noout -text | head -50

# Key fields to understand:
# Issuer: Let's Encrypt (the CA that signed it)
# Subject: CN=yourdomain.com (what it's for)
# Validity: Not Before / Not After (90-day validity)
# Subject Alternative Name: lists all covered domains
# Public Key Algorithm: shows the key type used

# See your certificate files
sudo ls -la /etc/letsencrypt/live/yourdomain.com/
# cert.pem      = your certificate
# chain.pem     = intermediate CA certificates
# fullchain.pem = cert.pem + chain.pem combined
# privkey.pem   = YOUR PRIVATE KEY (never share this)

Set up auto-renewal (certificates expire in 90 days):

bash — configure auto-renewal
# Test renewal process (dry run — doesn't actually renew)
sudo certbot renew --dry-run

# Certbot installs a systemd timer automatically
# Verify it's active:
sudo systemctl status certbot.timer

# Check the renewal schedule
sudo systemctl list-timers | grep certbot
Portfolio documentation pointWrite this down: "Let's Encrypt uses the ACME protocol with an HTTP-01 challenge to verify domain ownership before issuing a DV (Domain Validated) certificate. The certificate is signed by ISRG Root X1 (Let's Encrypt's root CA). Certificates are valid for 90 days and renewed automatically via a systemd timer. The private key is stored at /etc/letsencrypt/live/ with permissions 700, readable only by root."
PHASE 07 Harden TLS configuration
✓
STEP 08
Configure strong cipher suites & security headers
Get SSL Labs A+ rating
TLS HardeningCipher SuitesHSTS
▼
Why default TLS config is not enoughCertbot gives you a working certificate but doesn't enforce the strongest settings. Old TLS versions (1.0, 1.1) have known vulnerabilities. Weak cipher suites can be exploited. An A+ on SSL Labs proves you understand the difference — this is what separates an engineer from someone who just ran a command.

Edit your Nginx config to add hardened TLS settings:

bash
sudo nano /etc/nginx/sites-available/securitylab
nginx — full hardened config
# HTTP → HTTPS redirect (Certbot may add this automatically)
server {
    listen 80;
    server_name yourdomain.com www.yourdomain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name yourdomain.com www.yourdomain.com;
    root /var/www/securitylab/html;
    index index.html;

    # Certificate paths (set by Certbot)
    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

    # Only allow TLS 1.2 and 1.3 (disable old, vulnerable versions)
    ssl_protocols TLSv1.2 TLSv1.3;

    # Strong cipher suites only
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256;
    ssl_prefer_server_ciphers off;

    # Diffie-Hellman parameters for perfect forward secrecy
    ssl_dhparam /etc/nginx/dhparam.pem;

    # Session caching for performance
    ssl_session_timeout 1d;
    ssl_session_cache shared:MozSSL:10m;
    ssl_session_tickets off;

    # OCSP Stapling (faster cert validation for clients)
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/letsencrypt/live/yourdomain.com/chain.pem;
    resolver 8.8.8.8 8.8.4.4 valid=300s;

    # Security headers
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
    add_header X-Frame-Options DENY;
    add_header X-Content-Type-Options nosniff;
    add_header X-XSS-Protection "1; mode=block";
    add_header Referrer-Policy "no-referrer-when-downgrade";
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'";
    add_header Permissions-Policy "geolocation=(), microphone=(), camera=()";

    # Hide Nginx version number
    server_tokens off;

    location / {
        try_files $uri $uri/ =404;
    }
}

Generate Diffie-Hellman parameters (this takes a few minutes — the security math is intense):

bash
# Generate strong DH parameters (3–5 minutes to compute)
sudo openssl dhparam -out /etc/nginx/dhparam.pem 2048

# Test config, reload Nginx
sudo nginx -t && sudo systemctl reload nginx
What each header does — know this for interviews HSTS (Strict-Transport-Security): tells browsers to ONLY use HTTPS for this domain for 2 years, even if user types http:// X-Frame-Options DENY: prevents clickjacking (your site can't be embedded in iframes) X-Content-Type-Options nosniff: stops browsers guessing file types (prevents MIME-type attacks) server_tokens off: hides your Nginx version so attackers can't target known vulnerabilities

Intrusion PreventionPatch Mgmt

Why this mattersFail2ban watches log files and bans IPs that fail auth too many times. It's detective + preventive control combined. Unattended-upgrades ensures security patches apply automatically — one of the most common real-world vulnerabilities is simply unpatched software.
bash
# Install Fail2ban
sudo apt install fail2ban -y

# Create a local config (override defaults safely)
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo nano /etc/fail2ban/jail.local

Find and set these values in jail.local:

fail2ban jail.local — key settings
[DEFAULT]
# Ban for 1 hour after 3 failures in 10 minutes
bantime  = 3600
findtime = 600
maxretry = 3

[sshd]
enabled = true
port    = ssh
logpath = %(sshd_log)s
backend = %(sshd_backend)s
bash — enable Fail2ban & auto-updates
# Start Fail2ban
sudo systemctl start fail2ban
sudo systemctl enable fail2ban

# Check status and active jails
sudo fail2ban-client status
sudo fail2ban-client status sshd

# Install automatic security updates
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure -plow unattended-upgrades
# Select YES when prompted

# Verify it's configured
cat /etc/apt/apt.conf.d/20auto-upgrades
